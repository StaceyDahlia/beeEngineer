# beeEngineer
# BeeEngineer — планирование маршрутов выездных инженеров

Прототип интеллектуального сервиса, который распределяет заявки
между выездными инженерами, строит маршруты с учётом временных окон,
навыков и транспорта, показывает их на карте и умеет перестраивать
план при событиях в течение дня.

Разработан в рамках кейса «Билайн Бизнес».

---

## Быстрый старт

Требуется Python 3.10+.

```bash
# 1. Установить зависимости
pip install -r backend/requirements.txt

# 2. Выбрать сценарий данных (по умолчанию — east)
python backend/scripts/select_scenario.py east

# 3. Запустить API
uvicorn app.main:app --reload --app-dir backend

# 4. Проверить
curl http://localhost:8000/health
```

Первый запуск планирования:

```bash
curl -X POST http://localhost:8000/optimize \
  -H "Content-Type: application/json" \
  -d '{"scenario": "east"}'
```

Полный контракт API — в [`API_CONTRACT.md`](./API_CONTRACT.md).

## Сценарии данных

В проекте три синтетических сценария на один рабочий день:

| Сценарий | Заявок | Инженеров | Офис |
|---|---|---|---|
| `east` (по умолчанию) | 66 | 12 | ул. Юных Ленинцев, 83к4 |
| `southeast` | 83 | 12 | ул. Бирюлёвская, 1к1 |
| `southcenter` | 56 | 11 | Симферопольский проезд, 7 |

Переключение:

```bash
python backend/scripts/select_scenario.py east
python backend/scripts/select_scenario.py southeast
python backend/scripts/select_scenario.py southcenter
```

Скрипт копирует выбранный сценарий в `data/processed/`. Backend читает
именно оттуда. После переключения нужно перезапустить API (или очистить
кэш `loader.clear_caches()`).

## Как работает планирование

Пайплайн:

```
jobs.json + engineers.json
        │
        ▼
   loader.load_all()
        │
        ▼
   optimizer.optimize()
        │
        ├── distance.travel()        расстояние и время с пробками
        ├── constraints.can_assign() три группы ограничений
        ├── baseline.build_...()     для сравнения метрик
        └── explainer.explain_...()  тексты на русском
        │
        ▼
      Plan  →  API  →  frontend
```

Основные шаги `optimizer`:

1. **Сортировка заявок** — срочные раньше, потом по раннему концу окна,
   потом по длительности.
2. **Best insertion** — каждая заявка вставляется в лучшую позицию
   (маршрут × место в маршруте), где прирост пробега минимален и
   окна не ломаются.
3. **Локальные улучшения** (до 50 итераций):
   - `free_engineer` — освободить целого инженера, перенеся его заявки.
   - `2-opt` — уменьшить пробег внутри маршрута.
   - `swap` — обменять заявки между маршрутами.

Целевая функция **лексикографическая** (по ТЗ):

1. Сначала минимизировать число задействованных инженеров.
2. Затем — суммарный пробег.

То есть 2 инженера с пробегом 100 км лучше, чем 3 инженера с пробегом
80 км.

## Обязательные ограничения

Учитываются три группы (ТЗ п.2.2):

| Ограничение | Что проверяется |
|---|---|
| **Квалификация** | `job.skill ∈ engineer.skills` |
| **Время** | приезд в окно заявки; весь маршрут в смену инженера |
| **Ресурс** | если в заявке указан транспорт, у инженера должен быть такой же |

Если заявку нельзя назначить, в поле `explanation` возвращается
понятная причина: «нет навыка», «нет транспорта», «не успевает в окно»,
«не укладывается в смену», «все подходящие заняты».

## Обязательные метрики

Считаются в `metrics.compute(plan)`:

- `engineers_used` — сколько инженеров задействовано.
- `total_distance_km` — суммарный пробег.
- `unassigned_count` — сколько заявок не назначено.
- `per_engineer_distance_km` — пробег по каждому инженеру.

Всегда возвращаются **два набора**: `metrics` (результат optimizer) и
`baseline_metrics` (результат базового жадного алгоритма из ТЗ п.2.3).
Фронт показывает сравнение на плитках.

## Перепланирование

События в течение дня обрабатываются `replanner.replan(plan, event)`:

| Событие | Что происходит |
|---|---|
| `urgent_job` | новая срочная заявка вставляется в план |
| `cancel_job` | заявка удаляется из маршрута, освобождается слот |
| `engineer_unavailable` | инженер помечается недоступным, его заявки перераспределяются |

Ответ содержит:

- `changed_job_ids` — что изменилось.
- `diff_summary` — разбивка по типам изменений.
- `needs_review` — заявки, требующие решения диспетчера
  (например, `in_progress`-заявки недоступного инженера).
- `warnings` — структурированные предупреждения.

Заявки со статусом `in_progress` или `done` **не переназначаются**
автоматически — они заморожены до решения диспетчера.

## Известные ограничения

Это прототип, а не промышленная система. Что осознанно не сделано:

- **Оборудование не учитывается** (`check_equipment=False`).
  В `inventory.json` недостаточно стартовых остатков на все заявки;
  учёт оборудования резко увеличил бы долю `NO_EQUIPMENT`.
- **Расстояние — Haversine × 1.3** (коэффициент извилистости дорог).
  Реальная дорожная сеть не используется, OSRM не подключён.
- **Пробки — по профилю `typical.weekday`** из
  `reference/traffic_profiles.json`. Это параметры сценария, а не
  измеренные данные.
- **Общественный транспорт моделируется как единый modal split**
  (40 км/ч). Не разбит на metro + surface_transit + waiting.
- **Математический оптимум не гарантируется.** Используется жадный
  алгоритм с локальными улучшениями.
- **`geocoder.py` и `normalizer.py` — заготовки.** В рантайме
  не используются, потому что активные сценарии уже содержат координаты
  и нормализованные поля.
- **Нет авторизации, нет сохранения состояния на сервере.**
  Фронт держит `Plan` у себя.
- **Только один сценарий активен одновременно.** Переключение — через
  `select_scenario.py`, требует перезапуска.
